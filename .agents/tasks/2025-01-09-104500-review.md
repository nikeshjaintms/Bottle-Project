## High-level view

The system calculates available stock by summing total units, subtracting active allocations from both LacquerPlan (incomplete rows only) and Incoming orders, then comparing against requested order quantity. This calculation runs at preview time (informational), validated again at commit time (authoritative). Backend returns `STOCK_WARNING_REQUIRED` errors when users attempt to exceed available stock without acknowledgment; frontend prevents form submission until warnings are acknowledged.

Stock warning data flows through three paths: Excel import preview separates valid rows into OK and warning sections, allowing selective override per row. Single-row create and edit forms validate on Order Qty blur, displaying inline warnings with breakdown details. List view adds visual indicators (⚠️ badge with yellow highlight) for acknowledged overrides, allowing audit review later.

The implementation handles qty decrease correctly in edit mode (no warning triggered), prevents self-counting during edit by excluding the current row from allocation, and properly excludes completed rows (where `coatingCompletedQty >= orderQty`) from stock calculations. Database schema was extended with three fields to capture acknowledgment timestamp and warning snapshot for audit.

2. **Race condition between preview and commit — informational only** — If stock allocations change between when user sees the preview and when they click import (another user creates a plan), backend recalculates at commit time and catches the discrepancy. Second import will show warning on retry. This is acceptable; prevents double-booking. Noted as a design choice, not a bug.

3. **Incoming Plan field access assumption** — Code assumes Incoming records have `items` array and each item has `bottleId` and `qty` fields. If Incoming schema differs or has optional fields, allocation calculation could undercount. Verify Incoming schema matches usage in `calculateAvailableStock()`.

### Stock Calculation: Completing Rows Correctly Excluded

The `calculateAvailableStock()` helper uses MongoDB `$expr` to exclude completed rows: `$expr: { $lt: ["$coatingCompletedQty", "$orderQty"] }`. This comparison correctly identifies incomplete rows; rows where `coatingCompletedQty >= orderQty` are filtered out. Query also handles the deprecated `coatedQty` field alongside `coatingCompletedQty`, ensuring backward compatibility with older data. The TODAY boundary (`planDate: { $gte: today }`) correctly limits allocation to future dates, preventing double-counting historical completed work. Available stock is calculated as `MAX(totalStock - allocated, 0)`, properly handling the zero-stock edge case where any order quantity triggers a warning.

### Warning Validation Integrated Across Five Entry Points

Backend validates stock before insert/update at five entry points: `createPlan()`, `updatePlan()`, `previewImportExcel()`, `commitImportExcel()`, and `importPreviousDay()`. In `createPlan()`, any warning without acknowledgment returns `STOCK_WARNING_REQUIRED` error with full warning details. In `updatePlan()`, the validation is guarded by a qty-increase check (`if (newQty > oldQty)`), so decreases and unchanged quantities skip validation entirely — this is the specified behavior. In Excel flows, warnings are calculated during preview, then respected during commit; rows without override flag are skipped.

### Frontend Form Blocking Correctly Implemented

AddLacquerPlan and EditLacquerPlan both prevent form submission if any row has a stock warning without an acknowledgment checkbox checked. The condition `if (unacknowledgedWarnings.length > 0) { return Swal.fire(...) }` blocks the submit handler before the API call occurs. On blur of Order Qty field, the forms call `GET /lacquer-plan/validate-stock` with `bottleName`, `companyId`, `orderQty` parameters, store the warning object in state, and display an inline alert card with breakdown. In edit mode, the API call also passes `excludeRowId` to prevent the current row from being counted in its own allocation calculation.

### Excel Import Override Map Correctly Handled

`previewImportExcel()` returns two arrays per date: `okStockRows` and `warningStockRows`, plus a `stockWarnings` array with per-row indices for mapping. Frontend displays both arrays separately with override checkboxes only on warning rows. On commit, `commitImportExcel()` accepts a `stockWarningOverrides` map where keys are row indices and values are booleans. The function checks `if (stockWarningOverrides[rowIndex] === true)` before importing each warning row; non-overridden rows are skipped. Overridden rows get `stockWarningAcknowledged: true`, `acknowledgedAt: now()`, and `stockWarningDetails: warning object` stored as metadata.

### List View Badge and Tooltip Properly Wired

LacquerPlan list adds a new column showing `⚠️ Override` badge when `row.stockWarningAcknowledged === true`. The badge has `title` attribute containing override details, and Bootstrap `data-bs-toggle="tooltip"` to enable hover behavior. Row itself gets `table-warning` class for light yellow background. Badge displays: "Stock Warning: X units over | Order: N | Available: M | Acknowledged: DATE". This allows production support to identify and audit all acknowledged overrides in one view.

### Database Schema Correctly Extended

LacquerPlan schema now has three new fields: `stockWarningAcknowledged` (Boolean, default false), `acknowledgedAt` (Date, default null), `stockWarningDetails` (Mixed/JSON, default null). These fields persist warning metadata for audit trail and reporting. No migration needed; fields initialize to defaults for existing rows.

### Edge Cases Handled

Zero-stock scenario: available stock = 0, any order quantity > 0 triggers warning with `overBy = orderQty`. Completed rows: excluded via `$expr` check, so finished allocations don't block new orders. Qty decrease on edit: `newQty <= oldQty` condition guards the warning check, so decreases never warn. Multiple concurrent imports: recalculation at commit time catches allocation changes; second import sees updated stock and re-warns if needed.
